## Two-layer verification

**Layer 1 — SQL syntax lint** (`grade_parse.py`, sqlglot Oracle dialect):
```
stats: 178 examples, 160 SQL OK, 2 SQL parse-fail, 19 PL/SQL unverified,
       14 anonymous-block unverified
```
The 2 SQL "failures" are both the known `JSON_VALUE(... RETURNING NUMBER)`
sqlglot dialect gap — valid Oracle 12.2+ syntax that sqlglot's Oracle grammar
lacks, not real defects (confirmed to execute correctly in Layer 2). PL/SQL
bodies and anonymous blocks are marked unverified by the parser by design; the
live grader is the authority for them. See `grade_parse_report.json`.

**Layer 2 — live-Oracle execution grading** (`grade_db.py`): the high-signal
check. Every statement runs against a real instance; `expected` arrays assert
actual result values.

## Schemas used

- **GRADER** — scratch schema (created by the grader). Each example builds its
  own `CREATE TABLE` schema from its `input`, runs, then drops everything, so
  examples never collide. 91 examples.
- **HR** (`hr`/`HrTest_23ai`) — EMPLOYEES, DEPARTMENTS, JOBS, LOCATIONS,
  COUNTRIES, REGIONS, JOB_HISTORY plus the DEMO_OBJECT_* and DEMO_JSON_*
  families. Read-only queries. 34 examples.
- **CO** (`co`/`CoTest_23ai`) — CUSTOMERS, ORDERS, ORDER_ITEMS, PRODUCTS,
  STORES, INVENTORY, SHIPMENTS plus the DEMO_OBJECT_* / DEMO_JSON_* families
  and PRODUCT_REVIEWS / PRODUCT_ORDERS / STORE_ORDERS views. Read-only. 35 examples.
- **SALES_LAB** (`SalesLab_23ai`) — partitioned orders, regions, monthly report
  view, region materialized view, `LLM_SALES_ADD_ORDER`, `LLM_SALES_REGION_TOTAL`,
  `LLM_SALES_ORDER_AUDIT`, load-errors table. 9 examples.
- **DOCUMENTS_LAB** (`DocsLab_23ai`) — JSON invoice ingestion, normalized
  invoices, `LLM_DOC_PKG`, supplier report. 6 examples.
- **OPS_LAB** (`OpsLab_23ai`) — event/run logs and the disabled
  `LLM_OPS_HEALTH_JOB` scheduler job. 3 examples.

The HR/CO/lab schemas are NEVER wiped or modified — only read.

## Example format

```
{"instruction": "...", "input": "...", "output": "...",
 "schema": "HR"|"CO"|"SALES_LAB"|... (omitted=GRADER),
 "expected": [{"sql": "...", "value": <known-answer>}, ...]}
```

The `schema` field routes execution to the right connection. The `expected`
array lists queries whose first-column/first-row result must equal `value`; the
grader marks CHECK_PASS/CHECK_FAIL. This turns the grader from a
"does it compile" check into a "does it return the right answer" check.

## How to reproduce

```
docker compose up -d                     # start Oracle Free
# wait for 'DATABASE IS READY'
uv pip install oracledb
.venv/bin/python grade_db.py oracle_dataset_full.jsonl      # Layer 2 execution grading
.venv/bin/python grade_parse.py oracle_dataset_full.jsonl   # Layer 1 sqlglot lint
```

The grader auto-detects GRADER (creating it on first run via the system account
if needed) and connects to the sample/lab schemas directly. Full per-statement
detail in `grade_db_report.json`; parser detail in `grade_parse_report.json`.
